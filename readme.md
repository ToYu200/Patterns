# Паттерны в репозитории Patterns

### Состояние (State) — как *машина состояний*

**Где**: `frontend/src/context/MatchmakingProvider.tsx`, `frontend/src/context/matchmakingContext.ts`  
**Почему оно**: есть *состояние системы* («ищем/не ищем», выбранный режим/регион), и UI ведёт себя по-разному в зависимости от него.

Мини-пример «условного состояния» (UI реагирует на `searching`)

### Наблюдатель (Observer) — через React Context

**Где**: `frontend/src/context/MatchmakingProvider.tsx`, `frontend/src/hooks/useMatchmaking.ts`  
**Почему оно**: компоненты-«подписчики» автоматически получают обновления при изменении `value` провайдера.

### Стратегия (Strategy) — как *подмена политики отображения*

**Где**: `frontend/src/matchmakingLabels.ts`  
**Почему оно**: у вас есть «политика представления» значений (`mode`, `region`) в UI. Это напоминает Strategy как «выбор способа отображения».  

### Фасад (Facade) — как *тонкий удобный API* к подсистеме

**Где**: `frontend/src/hooks/useMatchmaking.ts`  
**Почему оно**: хук скрывает детали `useContext(MatchmakingContext)` и единообразно даёт доступ к матчмейкингу.  

### Адаптер (Adapter) — как *адаптация данных к UI-компоненту*

**Где**: `frontend/src/pages/FindMatch.tsx`  
**Почему похоже**: данные приводятся к форме, которую ждёт Mantine `Select` (`{ value, label }`). Это типичный мотив адаптера «привести к нужному контракту».

## Тренер: реализация четырёх паттернов

Основная реализация находится в `backend/internal/service/coaching.go`, а
демонстрационный endpoint — `GET /api/coaching/session?program=individual|team`.
Endpoint возвращает созданного тренера, программу занятия, планы учеников и
полученные ими уведомления. Во frontend результат доступен на странице
`/coaching`, где можно переключить индивидуальную и командную программу.

### Стратегия (Strategy)

**Задача**: тренер должен менять методику тренировки без изменения своего
алгоритма проведения занятия.

**Участники**:

- `TrainingStrategy` — интерфейс стратегии с методами `ProgramName` и `PlanFor`.
- `IndividualMechanicsStrategy` — упражнения на механику и реакцию.
- `TeamTacticsStrategy` — упражнения на коммуникацию и командные ротации.
- `TrainingCoach` — контекст, который вызывает выбранную стратегию.

**Зачем**: если понадобится программа по анализу матчей или подготовке к
турнирам, достаточно добавить новую стратегию; код тренера и API менять не
нужно.

### Наблюдатель (Observer)

**Задача**: ученики должны узнавать, что тренер начал занятие, без жёсткой
связи тренера с конкретным количеством учеников.

**Участники**:

- `TrainingObserver` — контракт подписчика.
- `Trainee.OnTrainingEvent` — обработчик уведомления ученика.
- `TrainingCoach.Subscribe` и `TrainingCoach.RunSession` — регистрация
  подписчиков и рассылка события.

**Зачем**: к уведомлениям можно подключить журнал, email-сервис или UI-события,
не переписывая проведение тренировки.

### Абстрактная фабрика (Abstract Factory)

**Задача**: создавать согласованный набор объектов для конкретного режима
обучения, а не собирать тренера, стратегию и группу вручную в HTTP-слое.

**Участники**:

- `CoachingFactory` — абстрактная фабрика продуктов `CreateCoach` и
  `CreateRoster`.
- `IndividualCoachingFactory` — создаёт тренера по личной механике,
  соответствующую стратегию и одного ученика.
- `TeamCoachingFactory` — создаёт тактического тренера, командную стратегию и
  группу учеников.
- `RunCoachingSession` — клиент фабрики: выбирает только семейство по параметру
  `program`.

**Зачем**: выбор режима одной строкой переключает целое совместимое семейство
объектов и не допускает комбинации вроде командной группы с неподходящей
методикой.

### Итератор (Iterator)

**Задача**: тренер должен проходить по ученикам, не зная, как группа хранится
внутри.

**Участники**:

- `TraineeRoster` — коллекция: быстрый доступ к ученикам хранится в `map`, а
  порядок записи отдельно фиксируется в `order`.
- `TraineeRosterIterator` — итератор с `HasNext` и `Next`.
- `RunCoachingSession` и `TrainingCoach.RunSession` — используют итератор для
  подписки учеников и построения индивидуальных планов.

**Зачем**: структуру хранения группы можно изменить, например на загрузку из
базы или очередь, не меняя код тренера.

### Проверка через API

```bash
curl "http://localhost:8080/api/coaching/session?program=individual"
curl "http://localhost:8080/api/coaching/session?program=team"
```

Для режима `team` фабрика создаёт тактического тренера и двух учеников,
стратегия формирует каждому командный план, Observer записывает уведомление о
начале занятия, а Iterator выполняет обход состава.
